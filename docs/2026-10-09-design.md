# aeris — Design Doc

Status: phase 1 implemented, 2026-10-09. Builds on `2026-10-09-next-steps.md`. Progress, decisions
and findings are tracked in `2026-10-09-tasks.md`.

## 1. Goals

A personal notes app with a single user, used two ways:

- **Humans** use a web UI that can be reached from anywhere via a URL.
- **AI agents** use a CLI that can run anywhere (laptop, cloud sandboxes, CI).

Priorities, in order: speed, simplicity, agent-friendliness (both for agents *using* the app and agents *writing* its code), and free or near-free infrastructure.

Non-goals for now: multiple users, `[[id]]` links between notes, pinning/starring, chunking long notes.

### Context that shapes the design

- The corpus is small: 25 notes and 24 KB as of today. Even 100× growth stays at a few MB.
- At this size, latency comes from network round-trips and cold starts, not from query execution or indexing.
- Neon (Postgres 18) already provides `pg_trgm`, `vector` (pgvector 0.8.6) and `pg_search`.

## 2. Architecture

```
            ┌──────────────────── Vercel (Hobby, free) ────────────────────┐
 Browser ──▶│  FastAPI (one Python function)                               │
 (cookie)   │   ├─ web routes: Jinja + htmx (HTML) ─┐                      │
            │   │                                   ├─▶ service layer ─────┼─▶ Neon Postgres
 CLI    ───▶│   └─ /api/*: JSON ────────────────────┘        │             │
 (Bearer)   │                                                └─────────────┼─▶ OpenRouter
            │  static/: built CSS, JS, vendored htmx (CDN)                 │    (embeddings)
            └──────────────────────────────────────────────────────────────┘
```

**One Python app, one deployment.** FastAPI serves two kinds of routes, and both call the same service layer in the same process:

- **Web routes** render HTML with Jinja and htmx, for the browser.
- **`/api/*` routes** return JSON, for the CLI and agents. The browser doesn't need this API.

**The server owns every database query and all business logic.** The CLI is a thin HTTP client.

- Agents running anywhere never hold database credentials. They only need a URL and a revocable token.
- The service layer exists once. Web routes and API routes are thin wrappers around it.
- The API is the stable contract for agents. The CLI's `--json` output is a near-direct passthrough.

**Frontend: server-rendered Jinja + htmx, styled with Tailwind v4 + daisyUI v5.**

- **The stack is already known**: Python and Jinja are familiar, and there's no second language or Node toolchain.
- **daisyUI** adds readable component classes (`btn`, `card`, `badge`, `input`, `menu`, `modal`) on top of Tailwind. That gives a polished look without building components in-house. Themes are CSS variables, so the existing palette can be kept.
- **`@tailwindcss/typography`** (the `prose` class) styles rendered Markdown, replacing the hand-written `styles.css`.
- **A small vanilla JS file** (`app.js`) handles client-side search filtering and keyboard shortcuts. Adopt Alpine.js only if several interactive pieces accumulate.

**Deployment:**

- FastAPI runs as a single Vercel Python function, in `lhr1` (London), next to Neon (`eu-west-2`).
- Static assets live in `server/static/`, mounted with `StaticFiles`. Vercel promotes the mount to its CDN, so they don't hit the function.
- Use Neon's **pooled** connection string and `NullPool`, which suits serverless.
- Deploys go through the Vercel CLI (`vercel deploy --prod` from `server/`), not Git integration.
- If cold starts turn out painful, slim the imports (e.g. drop the ORM in favour of plain psycopg). Measured in phase 1: 0.05–0.10 s warm, 1.8 s for a cold function (see §10).

### Alternatives considered

- **Vite + React + TypeScript + shadcn/ui.** It looks great and is very agent-friendly to write. Rejected because React and TypeScript are unfamiliar, so the code would be hard to review and maintain personally. It would also add a second stack (Node, a build pipeline, a second Vercel service) that none of the planned features need. Revisit only if the UI becomes heavily stateful (offline mode, a rich editor).
- **Next.js.** Rejected for the same reasons, plus the risk of logic leaking into TypeScript API routes and duplicating the Python server.
- **Basecoat UI** (shadcn/ui ported to plain HTML). Appealing, but its maturity and maintenance are uncertain.
- **Flowbite, Web Awesome, Pico, Bootstrap.** All viable. daisyUI won because it keeps templates readable, builds on the Tailwind setup already in place, and is mature.

## 4. Data model

```sql
CREATE TABLE note (
  id          serial PRIMARY KEY,
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now(),
  content     text NOT NULL,
  tags        text[] NOT NULL DEFAULT '{}',   -- derived from content on write
  deleted     boolean NOT NULL DEFAULT false
);

CREATE TABLE note_revision (                  -- snapshot of previous content on every update
  id          serial PRIMARY KEY,
  note_id     int NOT NULL REFERENCES note(id),
  created_at  timestamptz NOT NULL DEFAULT now(),
  content     text NOT NULL
);

CREATE TABLE note_embedding (
  note_id      int PRIMARY KEY REFERENCES note(id),
  model        text NOT NULL,
  content_hash text NOT NULL,                 -- sha256(content); mismatch ⇒ stale
  embedding    vector NOT NULL                -- no fixed dimension: switching models needs no migration
);
```

- **Titles are computed, not stored.** A title is the first non-empty line, with leading `#` and inline markdown stripped, truncated to about 80 characters. It's computed in `parsing.py`.
- **Tags are stored** so they can be filtered in SQL. They're recomputed on every write; `aeris-admin recompute-tags` backfills them.
- **Revisions** guard against an agent clobbering a note. The service layer writes one on every update and append. There's no UI for them at first.
- **Migrations** are numbered `.sql` files applied by `aeris-admin migrate` (a small script in `server/`), which records them in a `schema_migrations` table. For a schema this small, that's simpler than Alembic. They run as the owner role (see §8).

## 5. Parsing: tags, titles, normalization

**Tags.** (Revised 2026-10-09: explicit tag lines instead of inline tags.)

- Tags come only from lines starting with `Tags:` (any case), e.g. `Tags: #aeris, #project/notes`. A note may have several such lines, anywhere. A `#word` elsewhere in the note is not a tag.
- Within a tag line, a tag is `#` followed by a letter, then letters, digits, `_`, `-` or `/`. Unicode letters are allowed, and `/` allows hierarchy, e.g. `#project/aeris`. Pure numbers like `#12` are not tags.
- Tags are normalized to lowercase, deduplicated and sorted.

**Search normalization.** Unicode NFKD, then strip combining marks, then lowercase, then collapse whitespace runs to one space. So `Éte` matches `ete`, `ﬁle` matches `file`, and a phrase matches across a line break. This is implemented once in Python (`parsing.normalize`) for the server, and mirrored in `app.js` for the browser.

`parsing.py` gets thorough unit tests, since this is where edge cases live.

## 6. Search

### 6.1 Substring search (web): in the browser

1. **The sidebar is server-rendered with every non-deleted note**, newest first, with no pagination. Each item carries `data-search="{{ normalized content }}"` and `data-tags="..."`.
2. **On each keystroke**, `app.js` normalizes the query and hides the items whose `data-search` doesn't contain it. Query tokens starting with `#` filter on `data-tags` instead. There's no network call, and it takes well under 1 ms for thousands of notes.
3. **Matching items show a snippet** around the first match, computed in JS.
4. **After a create, edit or delete**, htmx re-fetches the sidebar partial, as it does today.

**Budget:** under 16 ms from keystroke to filtered results.

**Scaling escape hatch:** if the corpus grows to many thousands of notes, switch to a JSON index cached in `localStorage` and synced with `?since=`. That's not needed for the foreseeable future.

### 6.2 Substring search (CLI/API): on the server

(Revised 2026-10-09: filter in Python instead of `unaccent` + `ILIKE`.)

`GET /api/search?q=...` loads the live notes and keeps those whose `normalize(content)` contains `normalize(q)`. This is the same function the browser mirrors, so the CLI and the web UI always find the same notes. Each hit carries a snippet of the original text around the first match. At this corpus size, reading every note per search is negligible. If it ever isn't, store `normalize(content)` in a `search_text` column on write and query it with `LIKE` (plus a `pg_trgm` index if needed).

### 6.3 Semantic search

- **Model:** `openai/text-embedding-3-small` via OpenRouter's `/api/v1/embeddings`. It has 1536 dimensions (the column itself has no fixed dimension) and costs fractions of a cent for the whole corpus. The model name is config, so swapping models means changing config and running a reindex.
- **Text embedded:** the full note content. No chunking for now.
- **On write:** the service layer embeds inline right after saving (about 300 ms, 5 s timeout). If OpenRouter fails, the note still saves and is simply missing from semantic results until the next reindex.
- **Reindex:** `POST /api/admin/reindex` (also `aeris reindex`) embeds every note whose embedding is missing or has a mismatched `model`/`content_hash`. Requests are batched.
- **Query:** embed the query, then `ORDER BY embedding <=> :q LIMIT :k` (cosine distance). This is an exact scan with no ANN index, which is instant at this size. Results include a score.
- **Related notes:** reuses the note's stored embedding, so it needs no API call. Shown under each note in the web UI and available as `aeris related`.
- **In the web UI:** pressing Enter in the search box, or using the mode toggle, sends `hx-get /search?mode=semantic`. The ranked results replace the sidebar list. Semantic search never runs on every keystroke.

## 7. JSON API (CLI and agents)

All endpoints sit under `/api` and require auth.

| Method | Path | Purpose |
|---|---|---|
| GET | `/notes` | List notes. Params: `since`, `tag`, `limit`, `order`, `content=true\|false` |
| GET | `/notes/{id}` | One note |
| GET | `/notes?ids=1,2,3` | Batch fetch, so agents can load several notes in one call |
| POST | `/notes` | Create `{content}` |
| PUT | `/notes/{id}` | Replace `{content, expected_updated_at?}`. Returns 409 if stale. |
| POST | `/notes/{id}/append` | Append text, a safe primitive for agents |
| DELETE | `/notes/{id}` | Soft delete |
| GET | `/search?q=&mode=text\|semantic&limit=&tag=` | Search (`semantic` from phase 4) |
| GET | `/notes/{id}/related?limit=` | Semantic neighbours (phase 4) |
| GET | `/tags` | Tags with counts |
| GET | `/export` | JSON Lines dump of every note, including deleted ones |
| POST | `/admin/reindex` | Backfill embeddings and tags (phase 4) |

**Note shape:** `{id, title, tags, created_at, updated_at, content, deleted}`.

**Search hit shape:** `{id, title, tags, created_at, updated_at, snippet, score}`. The full content is omitted so agents can scan cheaply, then batch-fetch the notes they want. `score` is `null` for text search.

**Responses.** Lists are wrapped, so fields can be added later without breaking clients: `GET /notes` returns `{"notes": [...], "missing": [...]}` (`missing` lists requested IDs that weren't found, for batch fetches), `/search` returns `{"hits": [...]}`, and `/tags` returns `{"tags": [{"tag", "count"}]}`. A single note is a plain object. `POST /notes` returns 201 with a `Location` header; `DELETE` returns 204. Errors use `{"detail": "..."}`: 401 without a valid token, 403 for a read-only token on a write, 404, 422 for empty content or queries, and 409 for a stale edit, which also carries the note's `current` version.

**Optimistic concurrency:** the web editor also sends `expected_updated_at` (as a hidden field), so a human and an agent editing at the same time can't silently overwrite each other.

## 8. Auth (single user)

- **Tokens** are defined in a Vercel env var: `AERIS_TOKENS="me:rw:<secret>,agents:rw:<secret>,readonly:ro:<secret>"`. Each entry is a name, a scope and a secret of at least 32 characters; a malformed value fails loudly. Revoking an agent means removing its entry and redeploying.
- **CLI and agents** send `Authorization: Bearer <token>`.
- **Browser:** a `/login` page posts a token. The server sets an `HttpOnly; Secure; SameSite=Lax` cookie holding it, with a 1-year expiry. Unauthenticated web requests redirect to `/login` (htmx requests get `HX-Redirect`). `Lax` rather than `Strict` (revised 2026-10-09), so links from mail or chat arrive logged in; cross-site POSTs still don't carry the cookie.
- **Server checks:** one FastAPI dependency accepts either the cookie or the Bearer header, does a constant-time comparison against each configured secret, and rejects `ro` tokens on writes.
- **Database roles:** the server connects as `agent`, which can read and write rows but not change the schema. Migrations run as `neondb_owner`. Default privileges grant `agent` access to every table `neondb_owner` creates, so migrations need no `GRANT`s.

## 9. CLI

Configuration comes from env vars (`AERIS_URL`, `AERIS_TOKEN`), which suit agent sandboxes, or from `~/.aeris.yaml`. Env vars take precedence. The old CLI's `~/.aeris.yaml` holds `database_url`; the new one reads `url` and `token` instead.

```
aeris list   [--limit N] [--last "2 days"] [--tag T] [--json]
aeris show   ID [ID...] [--json]
aeris search QUERY [--tag T] [--limit N] [--json]        # exact substring
aeris ask    QUERY [--limit 10] [--json]                 # semantic
aeris related ID [--limit N] [--json]
aeris tags   [--json]
aeris add    [-m TEXT]            # else stdin if piped, else $EDITOR
aeris edit   ID [--stdin]         # else $EDITOR
aeris append ID [-m TEXT]         # else stdin
aeris delete ID
aeris export [PATH]
aeris reindex
```

- `--json` prints stable, documented JSON: the API shapes above. Without it, output is human-friendly.
- Errors go to stderr with a non-zero exit code. With `--json`, errors are printed as `{"error": ...}`.
- `list` shows the most recent notes, which fixes the current bug where it returns the oldest 30.
- `reset-db` and `web` leave the CLI. Maintenance moves to `aeris-admin` on the server side, which uses `AERIS_DATABASE_URL`. Local development uses `uv run fastapi dev server/main.py`.

**Agent skill (`skill/SKILL.md`).** A short document that teaches agents the workflow: search, then ask, then batch-show, then cite note IDs. It also covers when to use `append` versus `edit`, and the conventions for tags. It's installable as a Claude Code skill or pasted into `AGENTS.md`.

## 10. Web UI

- **Layout:** a sidebar with the search box, a semantic-mode toggle, tag filter chips and the note list (title, tags, relative date, snippet), plus a main panel. It's built from daisyUI components (`input`, `btn`, `badge`, `menu`, `card`), with the existing colour palette as a daisyUI theme.
- **Routing:** each note gets a real URL (`/n/42`). htmx swaps the main panel and uses `hx-push-url`, so links, back/forward and reloads all work.
- **Note view:** Markdown rendered server-side (`markdown2`, as today) inside `prose`, plus tags, dates, a related-notes section, and edit/delete actions.
- **Editor:** a daisyUI textarea with a preview toggle (rendered server-side via htmx). `Cmd+Enter` saves, `Esc` cancels. A 409 conflict shows a clear message.
- **Mobile:** the layout must work on a phone. The sidebar collapses to a list view, and the note opens full-screen.
- **Later:** full keyboard navigation (`/` to focus search, `j`/`k` to move through results, `e` to edit, `n` for a new note), implemented in `app.js`.

**Cold starts.** Opening a note is a server request: 0.05–0.10 s warm (measured from London), and about 1.8 s for the first request after the function has been idle, plus Neon's own wake-up. That's accepted as a baseline. If it bothers in practice, options in rising order of effort:

1. Prefetch notes on hover (htmx `preload` extension).
2. Embed every note's rendered HTML in the initial page and switch between notes client-side. This is cheap at today's size.
3. Slim the server's cold-start imports.

## 11. Agent-friendly development

These help coding agents work on aeris reliably:

- **`CLAUDE.md`** states the stack and pins versions: Tailwind v4 (CSS `@theme`, no `tailwind.config.js`), daisyUI v5 class names, htmx 2, Python 3.14. It also covers conventions (thin routes, logic in the service layer), and how to run, test, lint, type-check and rebuild CSS. This prevents the most common agent mistake: mixing syntax from different major versions.
- **Pinned, vendored assets** in `server/static/`, with no `@latest` CDN links. The in-browser Tailwind compiler (`@tailwindcss/browser`) is removed.
- **Tests:** unit tests (parsing, auth, routes that need no database) run offline. Database tests are integration tests against a Neon `test` branch (no real notes), each run in a throwaway schema, and marked `db`. Routes are tested through FastAPI's `TestClient`. These sit alongside ruff and pyright.
- **Seeing the UI:** during development the UI is checked in a real browser. A Playwright screenshot script, for coding agents without a browser, is in the backlog.

## 13. Risks & open questions

- **Cold starts** (measured): about 1.8 s for a cold function, plus Neon's wake-up. Acceptable for now; mitigations are listed in §10.
- **Dependency versions float** on Vercel, which installs `server/pyproject.toml` without a lock. Revisit if a deploy breaks.
- **The old CLI** writes to the same database until phase 2 replaces it, without creating revisions or computing tags.
- **Tailwind standalone CLI + daisyUI v5:** confirm the no-Node setup works as documented, including the typography plugin.
- **Domain:** a free `*.vercel.app` subdomain (today: `aeris-five-silk.vercel.app`), or a custom domain?
- Resolved in phase 1: Vercel's FastAPI entrypoint and static serving work as expected; `unaccent` isn't needed (§6.2).
