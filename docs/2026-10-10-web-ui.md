# aeris — Web UI Revamp

Status: 2026-10-10, brief and wishlist drafted. Follows `2026-10-09-design.md` (phases 1–5 done).
Tasks and progress live in `2026-10-10-web-ui-tasks.md`.

## 1. Context

The API and features are in a good place. The UIs need more work, starting with the web UI: the
basic features are fine, but a lot should change in terms of aesthetics. The CLI comes later.

What the web UI is today (design doc §10): a sidebar (New note, search box, tag chips, note list)
and a main panel (note view with Rendered/Raw, Edit, Delete; a textarea editor). Jinja + htmx 2,
Tailwind v4 + daisyUI v5 with a custom `aeris` theme, a small `app.js`.

## 2. How we work

### 2.1 Checking UI changes

What we learned in phases 3–4: driving a real browser against a local server catches bugs tests
don't (the daisyUI hint layout in 4.5), but each check cost a lot of setup (launch script,
throwaway token, seeding, cleanup), screenshots were sometimes taken before the page settled,
fixture notes were unrealistically short, and nothing covered dark mode or narrow windows.

So, before any visual work:

- **UI sandbox, one command.** Starts the dev server against the Neon test branch, seeded with
  realistic fixture notes (long, code blocks, tables, unicode, untitled, tagged and untagged), a
  fixed dev token from `.env` for instant login, and a fake embedder when there's no OpenRouter key
  (ranking works offline). Empties the test branch on exit. The user and Claude open the same URL.
- **Screenshot gallery (Playwright).** A fixed set of views (list, note, long note, editor,
  ranking, login), at desktop and narrow widths, saved to a folder. Taken
  before and after a change; Claude checks them, then sends the pairs for review. Waits for the
  page to settle, so no timing misreads.
- **Style guide page** (dev only). Every component on one page, rendered with the real templates
  and fixture data: list items, note view, editor, buttons, chips, ranking, errors. Most of the
  look lives in the daisyUI theme tokens, so this is where the overall feel gets tuned.

Dev-only code (sandbox, fixtures, style guide, screenshots) lives in `dev/`, outside `server/`, so
it stays out of the Vercel bundle. The sandbox: `uv run dev/sandbox.py`, then
`http://localhost:8765/dev/login`. Screenshots of the running sandbox:
`uv run dev/screenshots.py before` (then `after`), into `dev/screenshots/LABEL/` with an
`index.html`; gitignored. One sandbox at a time: they share the test branch, so a second one
refuses to start.

### 2.2 Iterating on aesthetics

1. **Direction first:** a short design brief (§3) before details: mood, density, typography,
   color, references. Screenshots of apps or sites we like beat adjectives.
2. **Mockups before code** for anything structural (layout, visual language): two or three static
   variants side by side; pick or mix, then implement.
3. **Polish passes:** observations come in batches; each batch becomes one task, reviewed with
   before/after screenshots and the sandbox, and committed once. Structural changes stay separate
   tasks.
4. **Show, don't tell:** a screenshot with a scribble is the best bug report.

## 3. Design brief

**Direction.** Functional and fairly minimal: a dashboard, where function comes first. Sans-serif
type. References (screenshots kept locally in `docs/aesthetics-inspiration/`, not committed): the
Vercel and Neon dashboards, and the OpenAI developer docs. What they share:

- **Near-monochrome.** White or near-white surfaces, a slightly grey sidebar, 1px light-grey
  borders and row dividers, black text. One accent, used sparingly (links, status, focus).
- **Black primary buttons** with an icon; secondary buttons outlined or light grey; pills are small,
  rounded, outlined.
- **Selection is a light-grey fill**, never an inverted (black) block.
- **Lists are rows**: equal heights, 1px dividers, muted metadata, relative times ("21m ago"),
  identifiers in monospace.
- **Inputs are visible**: 1px border, a search icon, sometimes a shortcut hint.
- **Code is light**: a very light grey block with a border and subtle syntax colors (OpenAI),
  not white on black.
- **One type scale**: ~14px for interface text, ~15–16px for reading, 12px muted metadata, bold
  page titles; medium weight for labels and buttons.

**Keep:** the layout. A top bar; a left pane with the notes; a right pane that shows or edits the
selected note.

**Color: a fresh start, a little color.** Retire the current maroon and mint theme (the user isn't
attached to it). Not pure greyscale either: minimal, with a little color. Neutrals slightly tinted
toward one hue (surfaces, sidebar, borders), and one accent used for primary actions, links, focus,
search highlights and a soft tint on the selected note. Candidates, compared side by side on the
style guide before choosing:

- **Slate + indigo:** cool blue-grey neutrals, an indigo accent.
- **Stone + emerald/teal:** warm grey neutrals, a green accent (closest to Neon).
- **Zinc + violet:** neutral greys, a violet accent.

**Light only:** no dark mode.

**Type (proposal).** Geist Sans for the interface and notes, Geist Mono for IDs and code (Vercel's
families, open source, vendored as files like the rest). Inter is the alternative. A coherent
scale fixes today's mismatches (tiny "New note" and "Delete", while note content reads well).

**daisyUI first.** Use daisyUI 5's components where they fit, and let them drive design decisions
rather than hand-rolling: e.g. `navbar`, `list` (rows), `menu`, `dropdown`, `input` (with icons),
`kbd`, `badge`, `join`, `tooltip`, `modal` (delete confirmation), `toast`, `skeleton` (loading).
Custom markup only where no component fits (the tag filter's type-to-filter checkboxes).

## 4. Wishlist

From the user (2026-10-10). IDs are for reference in tasks.

**Top bar**

- W1. Remove the user's name.
- W2. Move "New note" into the top bar.

**Sidebar** (needs the most work)

- W3. Every note takes the same height (today there's extra space after the first one).
- W4. Each item: the title; below it the note ID and last update as relative time ("3 minutes
  ago", as older versions of aeris did); below that the preview.
- W5. Visual separation between notes: a border or line.
- W6. Never scroll horizontally.
- W7. A new note appears in the list immediately (today it doesn't: to investigate).
- W8. The search box gets a visible border.
- W9. Tag filtering that scales to ~100 tags: a dropdown with a checkbox per tag, and typing filters
  the list of tags. daisyUI has a dropdown but no multi-select, so: a small component of our own
  (daisyUI dropdown, a filter input, checkboxes; logic in `app.js`), not a third-party library.
- W10. The selected note isn't black: rethink selection (see §3).

**Note pane**

- W11. A softer theme for content; code blocks in particular are white on black, too harsh.
- W12. The info at the top (ID, created, edited, buttons) becomes a full-width bar, with its bottom
  border running edge to edge (from the sidebar to the window's edge).
- W13. The bar stays put while the note scrolls.
- W14. Writing or editing uses the whole area below the bar, not a fixed-size text box.

**Later** (backlog): syntax highlighting in code blocks (` ```python `).
